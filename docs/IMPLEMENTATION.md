## 发送消息即时反馈（2026-10-30）

用户反馈发送后 5–10 秒才看见消息。核对 9f767286 的服务端时间线：收件后约 252ms 入队、352ms 开始执行，3.75s 出现原生 turn/start，5.15s 首次工具调用，19.27s 完成。该次不是执行队列顺序错误。进一步对照发现服务器 Caddy 2.6.2 对 SSE 使用 zstd，新增事件在压缩连接下被缓冲；同一事件在 identity 连接中 688ms 到达，在默认压缩连接 4 秒内未到。旧网页只从 Run 渲染用户消息，且 HTTP 回执后等待全局刷新，使发送过程也缺少独立可见状态。

- 只在工作台 SSE 路径且 Accept 为事件流时排除压缩，其他响应保持原设置；同时交付 Caddy 配置示例，避免再次引入缓冲。
- 点击发送即显示原消息与“发送中”，服务器确认后显示“已接收”；运行明确区分排队、启动和执行。
- 本标签页保存未完成提交，使用固定 eventId 与服务端 Message/Run 对齐。超时标记待确认，先查询回执，只有明确不存在时才以原 ID 和原请求体重试。
- 回执不再清空新输入或其他项目草稿；pending 与 Run 按 ID 合并，刷新和事件先到时也不会显示两条。
- SSE 的 run.updated 直接更新聊天；后台快照带请求时的序号水位，不能把新执行状态覆盖回旧状态。终态也不会被历史事件回放覆盖。
- 28 项普通 Go 行为测试、race、vet、TypeScript 构建通过；2 项前端状态合并测试通过。独立 Chromium 故障注入覆盖 5 秒延迟、全局刷新阻塞、回执丢失、核对重试、跨项目草稿和刷新去重，最后一次消息回显 39ms、全局刷新阻塞时运行显示 1153ms。
- 已发布 cloud-20261030-06-message-feedback；保留上一版和发布前完整快照。微信和飞书连接恢复为 connected，执行队列和模型配置沿用。
