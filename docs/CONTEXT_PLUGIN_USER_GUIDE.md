# 工具组件与上下文中心迁移：使用说明

本次在个人工作台加入通用组件入口，并独立部署上下文/批处理插件。工作台仍用SQLite保存项目、专家、Session和调用记录；25,126名用户的完整原始/清洗上下文在插件MySQL，工作台不承担客户数仓。

## 从哪里进入

1. 设置 → 连接与工具 → **工具组件**：查看所属项目、固定版本和允许动作，配置连接或停用。
2. 项目 → 原对话 → **运行配置**：选择专家、默认组件、动作、固定参数；保存不执行。用“按配置执行一次”运行，用“定时运行”设置/暂停Cron。
3. 专家库 → 专家 → 编辑基本信息 → **默认工具组件**：保存方法包引用。它只是推荐工具，不授予项目外权限。
4. 直接在项目对话里让专家工作。宿主用当前项目和Session代转工具调用，模型拿不到连接凭据。

## 已配置的七个工作入口

| 项目（均以“上下文中心 · ”开头） | 专家/组件的用途 | 默认操作 |
|---|---|---|
| 用户上下文维护 | 数据治理专家；拉取、清洗、查询、来源水位 | 固定程序同步 |
| 活动与批量生成 | 活动运营专家；沿原方案生成，或使用固定通用方案 | 先显示配置目录 |
| 服务计划与跟进 | 服务运营专家；原计划、策略和人工操作 | 先显示配置目录 |
| 关键用户推荐 | 用户推荐专家；原候选规则+证据解释 | 专家只读运行 |
| 报告与内容素材 | 报告内容专家；按确切用户读历史/素材 | 先显示配置目录 |
| 群运营 | 群运营专家；兼容原群运行状态和操作 | 先显示配置目录 |
| 经营分析与历史核查 | 经营分析专家；原指标、历史和回执 | 原分析纯读 |

原复杂业务仍由原中心执行。群视图、人工任务列表等某些GET接口会写文件或恢复任务，因此也归“本人确认的原系统操作”，不能被专家只读定时擅自调用。13个原定时只迁移参数和归属记录，执行权仍在原服务器；原Agent保持disabled。

另设两个新任务：每6小时20分拉取/清洗，每天09:10关键用户推荐，上海时间。它们只更新新数仓或在原Session输出，不发客户消息。首次启用、实际启用状态及下次时间以发布验收记录和工作台日历为准。暂停会阻止后续触发，已受理后台任务另在结果卡请求停止。

## 数据闭环

来源只读快照 → 流式分批写MySQL暂存代 → 身份/必需字段/别名链/异常跌幅校验 → 原始事实保留、仅约定字段格式清洗 → 原子发布水位 → Session查询与来源摘要。

失败或不完整快照不覆盖上一成功数据。保留当前/上一发布代；不会按昵称猜身份，不推断订单、权益或运营资格。`canonical.clean.v1`是实际安装的确定性规则，改版本标签不会凭空增加清洗逻辑。新增语义清洗需先由专家提出方法，再实现为独立插件规则；不自动执行模型临时生成的任意脚本。

精确查询动作`query_contexts`参数：

```json
{"user_ref":"usr_示例引用"}
```

身份清单动作`list_user_refs`：`{"limit":2000,"offset":0}`，它只是身份清单，不能当有效营销名单。推荐动作`recommend_users`复用原候选池；专家解释需引用实际返回证据，缺依据就待核。

## 一批生成2000条怎么用

先由活动专家确认场景、有效名单、原方案及素材版本。固定程序负责逐条执行、隔离上下文、限制并发和恢复。最新一期上限是**每批2000条**，更大名单拆批。

沿原提示词工程和资格校验生成时，用`batch_generate`：

```json
{
  "operation":"agent_copy_request",
  "parameters":{"service_pack_key":"weekly_review","scene":"weekly_review"},
  "items":["usr_示例引用1","usr_示例引用2"]
}
```

此例只说明参数结构，不能直接把示例身份当真实名单。`service_pack_key`、场景、内容身份和素材版本必须符合原计划；不适用时由专家沿原配置改参数。原接口生成和校验仍依赖原中心。

独立通用生成时，传`instruction`和`items:[{"item_key":"稳定编号","input":{"完整本条上下文":"..."}}]`。该模式只使用提供的单条输入，不会自动取得原业务的资格和素材门禁。需要原规则时使用上面的原方案模式。不要把全量客户正文塞进Harness对话，工具单批参数总量最多512KiB，单条自定义输入32KiB；大名单优先用身份引用。

后台任务显示成功数/总数。`batch_results`分页参数：

```json
{"task_ref":"结果卡中的jobRef","limit":20,"offset":0}
```

失败或停止后，用`retry`和同一个`task_ref`补未成功条目；已成功条目不重新生成。`next_offset`用于下一页。并发默认2，最大4；20次尝试后让出执行机会。真实2000条耗时和成本取决于模型/原接口，合成压力测试不代表2000条生产文案质量已人工验收。

## 确认、发送和异常

生成不等于发送。需要写原系统、审批或发送的操作先生成待确认卡，展示动作与参数；本人可以在页面确认，或在同一Session/渠道明确回复“确认组件 任务短码”。普通“发”或Agent转述不能替代这次精确确认；原系统仍会执行自己的审批和门禁。不要因为返回受理就宣布送达。

结果不明先刷新查回原任务；原系统操作不提供自动重试。后台停止以实际状态为准，已向原服务发出的动作不能用“取消”推定未执行。停用组件阻止新任务，在途任务仍需核查和收拢。

## 配置究竟迁到哪里

- 84份非私密提示词、策略及产品/Agent方法文件：原字节、来源SHA256、发布/草稿/归档状态保存在数据项目的“原中心配置”和插件只读资产目录；其他专家通过`read_configuration`按清单路径读取。
- 1份私密Agent运行配置、原连接及参考代码：存生产插件受保护的源配置归档；不进入专家公共包、对话、前端或Git。实际插件只读取所需源连接、模型连接和新MySQL连接。
- 13个原定时：参数和启用状态作为迁移记录，继续由原服务器执行，未复制消费者或自动发送任务。
- 专家方法包：统一边界与对应职责、默认组件标识；业务事实留项目/插件。原动态提示词拼装、发布覆盖、输出校验继续经兼容接口调用，不把几份MD当成完整原引擎。

因此当前不能关闭原中心。原数仓拉取、部分清洗、复杂计划、发送、原历史回执及对外关系API仍由原系统负责；新工作台提供统一操作入口与独立的数据/生成闭环。后续退役需逐项替代这些依赖并单独验收。

迁移脚本可重复运行：默认保留现有组件停用状态、专家修改、Session参数、目标、固定版本及定时暂停状态；导入默认与现有配置的差异写入受保护的preserved-customizations.json。显式--overwrite-existing才会覆盖，不把重跑当成重置。

## 回退

应用沿现有current/previous发布入口回退。旧版会冻结组件专家消息/Run和定时，不会将其误当普通可写任务执行。新插件数据保留，不能用旧工作台DB覆盖新业务数据；恢复新版后人工核对冻结任务，不自动补跑发送。原中心一直保留运行。
