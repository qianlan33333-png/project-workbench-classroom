# 使用与配置

日常入口是“今日”和项目对话。系统在后台运行 Harness Host、Temporal、通用 Worker 和消息连接器；业务资料、规则和任务记录在 MySQL，会话仍是 Harness 原生文件。

## 先用哪一处

| 要做的事 | 入口与方式 | 结果在哪里 |
|---|---|---|
| 安排工作、跨项目跟进 | 今日 → 进入今日对话，直接描述目标 | 今日对话、待决定事项 |
| 维护个人规则 | 今日 → 个人规则，添加、纠正或忘记 | 下一轮即使用当前版本 |
| 添加数据库/文件/HTTP资料 | 通用资源库 → 连接 → 资源 → 资料板块 | 更新版本、预览与校验 |
| 让另一个项目读资料 | 资源内勾选项目与板块，项目“引用资源”查看 | 共享默认只读；撤销后后续读取停止 |
| 定期拉取清洗 | 项目Session请专家调用 program_schedule | 今日的定时工作、原Session每轮反馈 |
| 批量生成 | 专家选择已发布资料板块、方法和人数，调用 batch_generate 或 program_run | 原Session任务编号、逐条产物、资源发布版本 |
| 看某轮进度或失败后继续 | 在原Session引用任务编号，查询 run_get/run_steps；需要时 run_resume | 原任务保留成功项，继续未完成部分 |
| 增加新能力 | 加资源配置、Skill方法或标准MCP连接器 | 无须新增业务专用后台 |

连接凭证由部署环境保存，模型和浏览器不拿到数据库密码。数据板块使用字段列表或 JSON Pointer 映射；输入预算由方法控制，超预算明确失败，不默默丢关键资料。

## 私域运营项目的实际配置

一个项目中承载数据维护与活动Session。项目专家是 `private-operations`；首次添加/变更本机Skill后，如已有会话未发现它，重新打开该会话或重启Host以重新发现。通用开发规则在 `workbench-tool-development`。

- `live-context-snapshot`：原上下文中心维护的完整HTTP快照，拉取后存入新MySQL。可选画像需求、权益关系、交互摘要、联系限制等板块；原文只供必要核查。
- `context-center-config`：136份原方法/配置文档及来源清单，共137个资料文件。保留原文并按需搜索；归档配置不自动启用所有旧定时任务。
- `original-followup-method`：原活动专家方法原文；`reviewed-followup-method`：保留原文并增加事实核验约束的版本。
- `activity-drafts`：尚未发送的生成产物，保留输入版本、方法摘要和生成时间。
- 数据维护定时：北京时间00:20、06:20、12:20、18:20，跳过重叠；今日汇总默认09:00。

例如在活动Session说：“使用当前发布的服务跟进方法，读取画像、权益、交互和联系限制，从已确认名单中生成40人的内部抽检草稿，不创建发送任务。”专家提交资源引用和人数；Worker每页最多200条、逐人切片、初始并发4，不把40/2000人的原文装进主对话。选择名单可用 `selection.recordIds`；数量可用 `selection.limit`，单次上限2000，续批使用返回游标。显式空名单会拒绝执行。

当前40人验收因缺少当次真实活动资格，全部输出阻断且文案为空。这证明约束工作，不能当成业务成稿通过。实际活动还需把计划/资格/可发送对象注册为资源，由标准校验确认；不能靠模型猜用户身份或营销计划。

## 抽检、发送与回执

批次先固定名单和正文，给本人抽检，确认对应审核码后才续办。微信/飞书为本人通知及决定入口。微信“受理”只证明平台接受；企微群发接口只创建手机待确认任务，员工手机确认后的回执才证明发送。未知状态先查原回执，不盲目重发。

当前没有创建客户发送任务。实际企微/其他客户渠道需在消息连接器配置有效凭证、来源身份映射及允许使用的项目；未配置时不能声称具备生产客户发送资格。

## 新旧系统边界

新工作台负责资源注册、MySQL版本、批量执行、原Session反馈、今日跟进及标准消息流程。原上下文中心仍负责其原有数据来源整理和业务计划，CRM继续提供业务事实；本期没有停止它们。旧工作台的程序/数据库不复用，新系统重新初始化；旧数据只保存在本机备份。

验收事实与待完成的上线步骤以仓库 `docs/IMPLEMENTATION.md` 为准，不能把文档中的配置计划当作已启用证明。
